# Memory Entry Schema & Templates

Memory files live in the project-root `.memory/` directory. Use concise
Chinese bullet points by default, or keep the project's existing language.
Use `⏳ unverified` for an untested hypothesis or incomplete validation;
`✅ verified` requires supporting evidence. Preserve existing entry formats.

## Daily File Template

When creating a new daily file `YYYY-MM-DD.md`:

```markdown
# YYYY-MM-DD Project Memory

> Auto-generated by AI Agent. Entries are append-only within a day.
```

## Entry Templates

### Problem

```markdown
---

<a id="problem-title"></a>
## [HH:MM] <short problem description>

**Type**: problem
**Tags**: `tag1`, `tag2`

- <What went wrong. Include symptoms and relevant evidence, without secrets.>

**Status**: ⏳ unverified
```

### Solution

```markdown
---

<a id="solution-title"></a>
## [HH:MM] Fix: <short solution description>

**Type**: solution
**Tags**: `tag1`, `tag2`
**Related**: [[YYYY-MM-DD#problem-title]]

- <Key code or configuration change and why it addresses the cause.>
- <Validation performed and the actual result; use unverified if not tested.>

**Status**: ✅ verified
```

### Optimization

```markdown
---

<a id="optimization-title"></a>
## [HH:MM] Optimize: <what was improved>

**Type**: optimization
**Tags**: `tag1`, `tag2`

<What was optimized and why. Include before/after metrics if available
(e.g. response time, build time, memory usage, accuracy).>

**Before**: <metric or behavior>
**After**: <metric or behavior>

**Status**: ✅ verified
```

### Decision

```markdown
---

<a id="decision-title"></a>
## [HH:MM] Decision: <what was decided>

**Type**: decision
**Tags**: `tag1`, `tag2`

<What was decided and the reasoning. List alternatives considered and why
they were rejected.>

**Alternatives considered**:
- <option A> — rejected because ...
- <option B> — rejected because ...

**Status**: ✅ verified
```

### Correction (marking a past entry as wrong)

```markdown
---

<a id="correction-entry-title"></a>
## [HH:MM] Correction: <what was wrong and the real fix>

**Type**: correction
**Tags**: `tag1`, `tag2`
**Corrects**: [[YYYY-MM-DD#original-entry-title]]

<Why the original approach was wrong. What the correct solution is.>

**Status**: ✅ verified
```

When writing a correction, also update the **original entry's Status** to:
```
**Status**: ❌ incorrect → see [[YYYY-MM-DD#correction-entry-title]]
```
or:
```
**Status**: ⚠️ superseded → see [[YYYY-MM-DD#better-entry-title]]
```

## Tag Conventions

Reuse these common tags before inventing new ones:

| Tag | Use for |
|-----|---------|
| `bug` | Runtime errors, unexpected behavior |
| `performance` | Speed, memory, resource usage |
| `config` | Configuration files, environment variables |
| `dependency` | Package versions, compatibility |
| `architecture` | System design, module structure |
| `security` | Auth, permissions, vulnerabilities |
| `test` | Test failures, test strategy |
| `deployment` | CI/CD, Docker, hosting |
| `refactor` | Code restructuring without behavior change |
| `workaround` | Temporary fix, not ideal |
| `data` | Data format, migration, schema |
| `ui` | Frontend, styling, layout |
| `api` | Endpoints, request/response |

## Cross-Reference Syntax

Use wikilink style: `[[YYYY-MM-DD#entry-id]]`. Replace the illustrative IDs
in the templates with real, unique IDs for each daily file.

- Add an explicit anchor immediately before each new entry heading, e.g.
  `<a id="redis-retry-1430"></a>`.
- Reference that exact ID: `[[2026-04-20#redis-retry-1430]]`. In plain Markdown
  use `[Redis retry](2026-04-20.md#redis-retry-1430)` instead.
- For old entries without explicit anchors, inspect the actual heading or add
  an anchor without rewriting the entry. Do not guess links from titles that
  omit the timestamp.
