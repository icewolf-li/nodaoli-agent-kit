# 编码与验证

- 先理解实际调用链、配置与现有实现，再改代码；优先修复根因。
- 保持改动范围与任务一致，沿用现有技术栈、命名、格式化和依赖管理方式。
- 能用现有依赖或标准库解决时，避免增加依赖；新增依赖说明用途。
- 使用项目现有的 formatter、lint、类型检查和测试命令。运行与改动风险相称的验证。
- 安装、更新、路径处理和文件覆盖逻辑必须验证；纯文案或低影响可逆修改不必添加机械复述实现的测试。
- 错误信息应包含可采取的下一步，失败不能静默继续或被包装成成功。
- 不将密钥、Token、真实个人数据或生产配置写入代码、日志、示例、记忆和公网仓库。
- 对接口、数据库、硬件配置等有外部影响的变更，检查现有使用方并记录必要的兼容性说明。
- 涉及近期变化的 API、版本或平台行为时，查阅官方文档；不要凭旧印象断言当前支持情况。
